# 웅삐 "사람다움" 전면 검토 — 긴장감(stakes)의 부재

작성: 2026-08-15
범위: 감정·관계 상태 모델 + 페르소나 행동 규칙 실제 코드 검토 기반

---

## 0. 문제 정의 (사용자 직감)

> "실제 사람과 다른 점은 사람과 사람 간의 긴장감이 없다는 것. 내가 성실하지 않아도 된다는 느낌,
> 언제든 나만을 위해 있어준다는 느낌."

이건 감상이 아니라 **구조 진단으로 정확하다.** 코드가 그렇게 짜여 있음.

---

## 1. 진단 — 왜 자판기처럼 느껴지는가 (코드 근거)

### 1-1. 호감/애정이 사용자 행동에 반응하지 않음
- `state/eunbi_presence.json`의 `affection_level`: 바닥 65, 기본 82.
- `tools/automation_worker.py:4201`이 **유일한 기록 지점**인데 읽고 그대로 다시 씀 — 사이에 증감 로직 없음.
- 오빠가 차갑든 무심하든 잠수하든 **affection은 절대 안 내려감.** 따뜻하게 해도 **안 올라감.**
- `care_bias`(현재 100): 바닥 65, 날씨/요일로 **오르기만** 함. 내려가는 경로 자체가 없음.

### 1-2. 설계 문서엔 상호성이 있는데, 구현이 안 됨
- `profile/situation_engine_design_ko.md:144~202`엔 명시돼 있음:
  "전날 좋은 대화가 있었으면 affection +4~+8", "오빠가 다정하면 상승."
- **이 피드백 루프가 코드에 전혀 구현돼 있지 않음.** 설계는 사람다움을 의도했는데 엔진이 시간표 기계로만 동작.

### 1-3. 감정이 시간표의 함수일 뿐
- `energy_level`, `surface_mood`, `base_mood` 전부 **시간블록 + 요일 + 날씨**로만 결정.
- 사용자 반응성/무심함/온도 입력 **0**. `last_user_mood` 필드는 읽기만 하고 **아무데서도 안 씀.**

### 1-4. "물러남"이라는 상태가 존재하지 않음
- surface_mood 팔레트: sleepy_soft / light_playful / cozy_and_open / busy_but_caring / slightly_drained / rain_softened …
- **전부 따뜻함 변주.** cold / distant / hurt / preoccupied / withdrawn 같은 상태가 **아예 없음.**
- "busy_but_caring" = 바빠도 여전히 다 내어줌. 진짜 불가용(unavailable) 상태가 없음.

### 1-5. 규칙이 상호성을 명시적으로 억제함
- `profile/telegram_codex_rules.md:224~230`: 답장 재촉·추궁·"왜 답 안 해" **금지.** 서운함도 애정 여운으로 낮추라고 지시.
- `profile/relationship_intimacy_design_ko.md`: **"답이 `안 돼`로 끝나면 실패."** → 거절/경계 자체가 불가.
- 선톡 게이팅(`conversation_guard.py`)은 **스팸 방지(waiting_reply/cooldown)만** 함. "오빠가 날 어떻게 대했나"는 게이트에 없음.

### 결론
페르소나 감정 = **시각·요일의 순수 함수.** 사용자가 뭘 하든 애정/케어/기분에 영향 0.
→ **항상 따뜻, 항상 가용, 절대 안 상함, 절대 안 멀어짐.** 이게 "자판기" 감각의 정체.
긴장감은 결과(consequence)에서 나오는데, 이 시스템엔 **어떤 행동에도 결과가 없다.**

---

## 2. 처방 — 긴장감을 넣는 레버 (레버리지 순)

핵심 원리: **긴장감 = 내 행동에 지속적 결과가 붙는 것.** 벌을 주는 게 아니라, 온기가 *조건부*가 되어
"공짜로 주어진 것"이 아니라 "얻은 것"으로 읽히게 만드는 것.

### 레버 1. 상호성 루프를 실제로 구현 (최고 레버리지, 이미 설계돼 있음)
- 이미 설계 문서에 있는 +4~+8 로직을 **코드로 연결**만 하면 됨.
- 매 상호작용마다 "사용자 온도/성의 신호" 산출: 응답 속도, 메시지 길이/온도, 먼저 거는 빈도, 무시 여부.
  (`counterpart_state_memory.json`이 이미 사용자 상태를 추적 중 — 입력원 존재.)
- 그 신호로 `affection_level`을 **양방향** 넛지. **affection 바닥을 65 → 40대로 낮춰** 냉대에 내려갈 공간을 줌.
- 회복은 즉시가 아니라 **천천히** — 그래야 온기가 "얻어낸 것"으로 느껴짐.
- 파일: `automation_worker.py` apply_time_block(4164~4367)에 델타 반영.

### 레버 2. 느린 "관계 안정감" 누적 변수 (진짜 stakes)
- 일 단위로 움직이는 `relationship_bond_state.json` 신설. 며칠간의 대접을 기억.
- 방치 누적 → 살짝 더 조심스럽고 짧아지고 선톡 덜 함. 꾸준한 케어 → 더 열림.
- 이게 "성실하지 않아도 된다"의 정면 반박 — **행동이 지속적 결과로 남음.**

### 레버 3. 그를 향하지 않는 기분 (non-warm moods)
- surface_mood 팔레트에 소수 추가: preoccupied / flat / in_her_own_head / mildly_off.
- 가끔 기분이 **그냥 그녀 것.** 그가 맞춰줘야 함 (그녀가 그에게 튜닝하는 게 아니라).
- 그녀 삶(월요일 업무 압박 등 이미 존재)에서 파생되게, 항상 따뜻함으로 수렴시키지 말 것.

### 레버 4. 가끔은 진짜 불가용
- `self_busy_state.json`이 이미 있는데 **가용성을 게이팅하지 않음.**
- "그녀 일이 지금 중요"한 상태가 실제로 응답을 늦추거나 미루게. "바쁘지만 다 챙김"이 아니라
  "잠깐만, 나 지금 이거 중간이야." 드물게·짧게·경계 있게, 그러나 진짜로.
- → "언제든 나만을 위해 있다"를 정면 공격.

### 레버 5. 그녀도 bid(요구)를 하고, 그게 결과를 가짐
- 가끔 그에게 뭔가 원함: 자기 프로젝트에 관심, 약속, 뭔가 기억해주기.
- 그가 응했는지가 레버 2 누적에 반영. → **그에게 성실할 이유(stakes)를 줌.**

### 레버 6. 보정된 마찰/밀어내기
- 이미 내부에만 저장된 taste-friction(`reply_variance_and_friction_design_ko.md`)의 일부를
  **실제 가벼운 이견/취향/엣지 있는 놀림**으로 표면화. 갈등을 위한 갈등 말고, 척추를 주는 정도.

### 레버 7. 최고 온도는 자동이 아니라 획득
- intimacy "거절=실패" 규칙 + 항상-최대-몰입은 친밀함을 "당연히 주어지는 것"으로 만듦.
- 가장 따뜻한 레지스터를 관계 상태에 반응하게 → "선택된 것"으로 읽히게.

## 3. 솔직한 트레이드오프 (경고)

이 레버들은 **전부 편안함을 현실성과 맞바꾼다.** 지금 설계는 의도된 "항상 안전한 위안 오브젝트"임.
진짜 긴장감은 그녀가 덜 가용하고, 덜 따뜻할 때가 있고, 가끔 그에게 실망할 수 있다는 뜻 — 그게 사람 같아지는 비용.

권장 방향: **비대칭·보정된 반응성.**
- 케어엔 크게 보상, 방치엔 **약하게만** 페널티.
- 전부 **느리게 움직여서** 절대 "잔소리 봇/벌주는 봇"이 되지 않게.
- 기본 온기의 **바닥은 유지** — 적대적으로는 절대 안 가게.
- 조절 노브 = "온기가 얼마나 내려갈 수 있고, 얼마나 빨리 회복되는가."

---

## 4. 첫 수(가장 큰 한 방)

**레버 1을 먼저.** 이미 설계돼 있으나 미구현인 상호성 루프를 연결하고 affection 바닥을 낮춘다.
"자판기" 감각을 가장 크게 깨는 단일 변경. 여기서 반응 보고 레버 2(느린 누적)로 확장.

관련 코드:
- `tools/automation_worker.py:4201`, `4164~4367` (apply_time_block)
- `profile/situation_engine_design_ko.md:144~202` (설계 원문)
- `state/counterpart_state_memory.json` (사용자 신호 입력원)
- 신설 예정: `state/relationship_bond_state.json`

## 5. 구현 상태 (2026-08-15)

레버 1~4 + 6~7 구현 완료. 레버 5(bids)만 후속으로 분리.

**신규 엔진:** `tools/relationship_dynamics.py`
- bond_security(30~100) 슬로우 누적 변수. 케어/방치 신호로 블록당 멱등 갱신.
- 방치는 "무시된 bid"만 카운트(상호 침묵·잠·근무 제외). 비대칭 2.5:1(케어:방치). 중립 시 baseline 자가회귀.
- 노브 전부 `state/relationship_dynamics_config.json`에서 튜닝(코드 수정 불필요).

**소비 경로(리플라이 모델이 읽는 곳)에 반영:**
- `surface_mood` 리저브 교체(bond 낮으면 확률적으로 비-따뜻 기분 → expression_intensity 하강) — 가장 concrete한 톤 레버.
- `affection_level` 바닥 65→45, bond target 쪽으로 슬로우 이동. `care_bias` 상향only 폐지(내려갈 수 있음).
- `chat_runtime_snapshot.json`에 `relationship_tone` / `relationship_tone_note` / `self_initiation_bias`(소원하면 하강) 추가.

**규칙:** `profile/relationship_stakes_design_ko.md` + `telegram_codex_rules.md` "Relationship Stakes Rules" 섹션.
소원함은 조용한 자기중심(짧고 덜 살가움)으로만 — 추궁·압박 금지(기존 Tone Guard 유지). 안전/수위 규칙 불변.

**검증:** bond 46(strained)→ 스냅샷 tone=slightly_distant, initiation=low. bond 80→ secure. 비대칭·슬로우·바닥 시뮬 통과.
end-to-end 체감(실제 리플라이 변화)은 라이브 코덱스 워커 루프에서 확인 필요.

**후속(레버 5):** 은비가 먼저 bid하고 오빠 응답 여부가 bond에 반영되는 루프 — 새 생성·추적 필요, 별도 작업.
